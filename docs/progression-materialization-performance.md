# Фоновая материализация прогрессии: замеры и проверка

23.10.2026. Baseline: `53cf43b067cfa3e5778fd35d7a3de320eb67dbc6` (main после #458).
Числа ниже получены на локальном синтетическом стенде Windows, **не на VPS**.
Машинные результаты, хэши и выбранные планы SQL: [benchmark JSON](progression-materialization-benchmark.json).

## Путь данных и уже существовавшая инкрементальность

`lib/progression-db.ts` сохраняет снимок, исправляет повреждённые/обогащённые данные
и вызывает нормализацию истории соответствующего игрока. Триггеры снимков и профилей
увеличивают `progression_personal_revisions`; нормализация сохраняет ревизию и версию
правил в `progression_normalizations` в той же транзакции. Фоновый regular-worker
уже пропускал неизменившиеся истории. Это сохранено: на стенде повторный расчёт
нормализует 0 игроков, добавление 1% снимков — 20 игроков.

`refreshSqliteProgressionAggregates()` строит оценки всей группы рейдов и агрегаты.
До этой работы общий временный источник интервалов уже исключал повторное чтение
исходной базы для каждой группы. Поддержка точечного `targetBucket` также существовала.
Оценки интервалов уже обновлялись условно; повторный запуск не переписывал равные scores.

`materializeSqlitePopulationSnapshot()` строит десять метрик, ориентиры риска,
достижений, распределения процентилей и опубликованное среднее. Завершённый payload
и указатель `progression_population_current` записываются атомарно. HTTP получает
опубликованное среднее через `readPublishedProgressionAverage()`; персональные
запросы timeline ограничены AID, популяционная часть берётся из публикации.
Тяжёлые вычисления остаются в отдельном worker.

Публикация achievement baseline из `players.db`, backfill её risk references и
экспериментальный achievement-tempo из #458 не объединялись с этим расчётом.
`ops/materialize-publications.sh` сохраняет отдельный третий процесс tempo.
Его даты, исключения/баны, кэш, deadline и расписание не менялись.

## Что тормозило и что изменено

Планы baseline показывают четыре чтения и сортировки снимков для cumulative-метрик,
шесть чтений и сортировок интервалов для rate-метрик. Один интервал шесть раз
проходил построение одних и тех же производных величин. При этом публикация занимала
больше времени, чем уже инкрементальная нормализация и агрегаты вместе.

Теперь оба источника читаются и сортируются по одному разу. Компактные временные
таблицы переиспользуются для метрик; шесть rate-величин вычисляются один раз на
интервал прежней функцией. Чтение по `rowid` сохраняет исходный порядок и развязку
равных значений без повторной сортировки. Это опирается на документированный
[порядок rowid при CTAS](https://sqlite.org/lang_createtable.html).
JS по-прежнему удерживает только текущее адаптивное окно одной метрики.

В агрегатах оконная сортировка больше не переносит `s.*` с полным `stats_json`;
избыточная сортировка перед созданием индекса временного источника удалена.
Итоговые строки `daily_aggregates` сравниваются по ключу и значениям: исчезнувшие
удаляются, изменённые обновляются, равные сохраняются.

Новый журнал затронутых групп не вводился. Полный worker продолжает пересчитывать
всю популяцию: один игрок меняет процентильные оценки других членов группы,
а адаптивные окна и распределения по наигрышу выходят за границы одного игрока.
Нынешних персональных ревизий недостаточно для доказанного отслеживания всех
старых/новых групп при удалениях и смене принадлежности. Измеренный выигрыш получен
без такого усложнения и без сокращения истории или выборки.

## Транзакции, конкурирующая запись и восстановление

Подготовка каждого результата читает согласованный снимок. Read SAVEPOINT
завершается **до** короткой транзакции записи: иначе любой параллельный commit
создаёт `SQLITE_BUSY_SNAPSHOT` при попытке получить writer. Это подтверждено
критиком, исправлено и покрыто тестом с commit на каждой попытке.
[Семантика WAL snapshot isolation](https://www.sqlite.org/isolation.html).

Перед записью scores сравниваются исходные поля интервала и персональная ревизия.
Добавленные после снимка интервалы не обнуляются; изменённые не получают старые
оценки. CAS поколения агрегатов не даёт старому расчёту заменить более новый
завершённый refresh. Целая популяционная публикация отражает данные на начало её
расчёта; более поздние снимки обрабатываются следующим штатным запуском. Шестичасовой
период и проверки свежести сохранены.

Идентификатор population generation выбирается под writer lock отдельно от
`generatedAt`. Откат часов не может переключить указатель на старый payload с тем
же timestamp. Более позднее завершённое задание защищено от старого строителя.
Очистка сохраняет фактическую текущую строку и ещё одну целую публикацию, включая
ремонт future-dated состояния. При ошибке commit указатель и payload откатываются
вместе; временные таблицы очищаются. Реальный выход дочернего процесса посреди
подготовки и записи проверен с повторным открытием и `quick_check`.

## Сопоставимый стенд

Один и тот же генератор: 2 000 игроков, 24 снимка на игрока (48 000 всего),
46 000 интервалов, 2 048 символов padding в JSON каждого снимка, восемь диапазонов
наигрыша. Для малого обновления добавляется один снимок каждому из 20 игроков.
Обновления сравниваются с полным расчётом, а не только с изменившимися игроками.

Node 24.19.0, SQLite 3.53.3, `--max-old-space-size=128`, одна файловая система,
одинаковый временный каталог и PRAGMA для обеих версий: WAL, synchronous=2,
cache_size=-2000, temp_store=0, page_size=4096. Версии запускаются последовательно.
Настройки стенда не являются предложением менять production PRAGMA.

«Первый» означает свежий процесс/данные без нормализаций и публикации. OS cache
не сбрасывался; создание fixture уже прогревает файловый кэш. «Без изменений» —
очередная публикация после истечения 6 часов, а не существовавший быстрый skip
свежей публикации. Время генерации, checkpoint и хэширования исключено из времени фаз.

| Сценарий | До, s | После, s | Сокращение времени |
|---|---:|---:|---:|
| Первый расчёт | 40.43 | 37.61 | 7.0% |
| Очередной без изменений | 12.63 | 8.84 | 30.0% |
| Новый снимок у 1% игроков | 12.78 | 9.14 | 28.5% |

Очередной запуск без изменений по фазам:

| Фаза | До, s | После, s |
|---|---:|---:|
| Нормализация | 0.08 | 0.06 |
| Агрегаты | 2.40 | 2.37 |
| Публикация | 10.15 | 6.40 |

Постоянные и временные записи:

| Сценарий | WAL до / после, bytes | Прямые изменения до / после | Финальная запись агрегатов до / после, ms |
|---|---:|---:|---:|
| Первый расчёт | 7473712 / 7473712 | 92084 / 92084 | 169.1 / 237.8 |
| Очередной без изменений | 370832 / 341992 | 165 / 3 | 37.6 / 31.3 |
| Новый снимок у 1% игроков | 6826872 / 6830992 | 11667 / 11565 | 144.6 / 242.2 |

При неизменном результате: 81 строка агрегатов больше не удаляется и не вставляется заново; 162 лишних изменения исключены. Полный payload всё ещё получает очередное поколение. WAL без изменений уменьшился на 7.8%. На малом обновлении WAL не снизился: основной объём создают изменившиеся оценки группы, а не 20 новых игроков.

Максимальный RSS процесса: 285.0 → 289.2 MiB. High-water temp SQLite: 7.40 → 12.41 MiB. Временное место выросло; увеличение не скрыто за уменьшением времени.


`persistedRowChanges` считает прямые изменения таблиц интервалов, агрегатов,
материализаций и публикаций, включая первоначальную вставку интервалов при
нормализации; не считает временные строки и побочные записи триггеров.
`total_changes()` включает temp-записи, поэтому отдельно сохранён в JSON.
Временных числовых строк стало больше: это обмен повторных чтений/сортировок
исходных данных на переиспользуемый компактный источник.

`commitSectionsMs` — верхняя граница времени участка финальной записи, включая
получение блокировки и commit; это не kernel-трасса точной длительности SQLite lock.
В JSON приведены все три сценария, включая возможное удлинение первоначального
writer-участка из-за проверки изменившихся входов. Отдельные WAL-соединения успешно
читают опубликованные данные и пишут во время подготовки. Синтетический HTTP-server
в отдельном Node-процессе использует реальный `readPublishedProgressionAverage`:
в последней целевой проверке 8 ответов HTTP 200, max 24,5 ms. Это не Next.js/VPS p95.

## Точность и обязательные проверки

Во всех трёх сценариях полностью совпадают SHA-256 payload, всех строк интервалов
и всех строк агрегатов до/после. Не округлялись значения для сравнения. Дополнительно
проверены шесть rate-метрик против прежнего построителя серии и влияние изменения
одного игрока на оценки другого участника группы.

Новые регрессионные проверки покрывают нулевые повторные записи агрегатов,
удаление опустевшей группы, баны и восстановление, изоляцию regular/PvE/сезонов,
смену score version, замену файла источника по тому же пути, непрерывные нерелевантные
commits, поздние новые/изменённые интервалы, более новое завершённое задание,
ошибку commit, аварийный выход, повторный запуск и откат часов с коллизией timestamp.
Существующие проверки покрывают новые снимки, parser enrichment, устаревшие версии
нормализации, retries и даты публикаций. Две memory-проверки сохраняются: 94 MiB
сырого JSON и 120 000 снимков / 110 000 интервалов при JS heap 64 MiB.

Локально пройдены целевые проверки, typecheck, i18n (2 040 ключей), lint без ошибок
(существующий warning `HomeComparison.tsx:113`), production audit (0 уязвимостей).
Полный Node 22 suite, systemd validation и Docker build/runtime проверяются
обязательным workflow PR. GPT‑6.1 Sol High после исправления двух найденных
дефектов дал чистое заключение и выполнил выбранные concurrency-регрессии.

## VPS и пределы выводов

Read-only проверка 23.10.2026: 1 CPU, 1 967 MiB RAM; shared background slice:
CPU 50%, RAM 512 MiB, swap 256 MiB, IORead 8 000 000 B/s, IOWrite 4 000 000 B/s.
Effective Compose из `/opt/tarkovstats-auto`, используемого background wrapper:
worker 0,5 CPU, mem_limit 536 870 912, memswap_limit 805 306 368, правильный
cgroup_parent, без опубликованных портов. Одноразового общего worker в момент
первой проверки не было. Production-конфигурация, расписания и лимиты не менялись.

Это синтетический локальный стенд, не репрезентативная копия всей VPS-базы:
распределение истории, сжатие, cache misses и конкуренция диска отличаются.
Физические байты I/O и Linux PSI этим стендом не измеряются; число проходов,
SQL-планы, WAL и выделенные temp-страницы не подменяют аппаратную I/O-трассу.
`tempAllocatedBytes` — high-water страниц временной SQLite БД, а не весь пик
диска с transient sort files. RSS — максимум процесса со времени старта, не сумма
контейнеров и не независимый пик каждой фазы. Влияние на VPS HTTP p95 и итоговый
nightly-cycle ещё требует отдельного наблюдения после разрешённого merge/deploy.
Историческое PSI 87–89% от 22.10 не объявляется текущей постоянной перегрузкой.

## Воспроизведение

Подготовьте отдельный checkout baseline `53cf43b` и этот checkout. Укажите абсолютные
пути обоих checkout, запускайте один и тот же скрипт и Node последовательно:

```sh
node --max-old-space-size=128 --experimental-strip-types scripts/benchmark-progression-materialization.mjs /path/to/baseline /tmp/before.json
node --max-old-space-size=128 --experimental-strip-types scripts/benchmark-progression-materialization.mjs /path/to/candidate /tmp/after.json
```

`BENCH_PLAYERS`, `BENCH_SNAPSHOTS`, `BENCH_PADDING` и `BENCH_TMPDIR` позволяют
повторить другой масштаб; задавайте одинаковые значения для обеих версий.
Базы создаются в новом временном каталоге и удаляются после закрытия соединения.
Production-файлы не читаются. Полные планы и отдельные счётчики сохраняются в
указанном JSON. Расширение масштаба требует подходящего дискового места и RAM;
измерения этого отчёта относятся только к указанному набору.
